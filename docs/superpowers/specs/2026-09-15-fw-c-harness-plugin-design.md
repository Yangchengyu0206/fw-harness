# fw-c-harness plugin design

- Date: 2026-09-15
- Author: Yang cheng
- Status: draft, under review
- Translation: [繁體中文](2026-09-15-fw-c-harness-plugin-design.zh-TW.md) (this English version is the source of truth)

## 1. Goals

An open-source plugin that gives every member of a firmware team, with a single install:

1. **A harness**, generated by a skill into their own C firmware repo: entry documents, state files, verification gates, git hooks, and architecture documents.
2. **Skills** for the whole work loop: starting a session, picking a ticket, implementing, reviewing, debugging, and wrapping up.

Constraints:

- Must work with both **Claude Code** and **GitHub Copilot**.
- **Several people work on the same codebase.** Every state change records the person who made it, and parallel work must not cause ticket ID clashes or frequent merge conflicts.
- Default toolchain: GCC (`arm-none-eabi`) with CMake, host `gcc` running Unity tests, `cppcheck`, `clang-format`.
- MISRA C:2012 is a **reference standard only**: advisory by default, configurable per project.

### Non-goals

- Built-in configuration for IAR/Keil, Zephyr, or ESP-IDF (the docs give substitution guidance only).
- Flashing production boards automatically, or providing a HIL test framework.
- GitHub Issues integration. Tickets live in the repo.
- Shipping MISRA rule text (it is copyrighted). We list rule numbers with our own one-line summaries.

### Language and license

- Everything is written in English: code, comments, CLI and error messages, skills, and documentation. The spec and the README also ship a Traditional Chinese translation (`*.zh-TW.md`); English is the source of truth.
- Content a team's harness produces for humans (review reports, commit messages drafted by `fw-done`) follows `language` in `harness/config.json`, default `en`.
- License: MIT. Content adapted from [awesome-copilot](https://github.com/github/awesome-copilot) and [mattpocock/skills](https://github.com/mattpocock/skills) (both MIT) credits its source in the file header and in `THIRD_PARTY_NOTICES.md`.

## 2. Distribution

One git repo is a marketplace for both tools:

```
fw-harness/
├─ .claude-plugin/marketplace.json     Claude Code: /plugin marketplace add <repo>
├─ .github/plugin/marketplace.json     Copilot: copilot plugin marketplace add <repo>
├─ plugins/fw-c-harness/
│  ├─ .claude-plugin/plugin.json
│  ├─ .github/plugin/plugin.json       lists the same skills
│  ├─ skills/                          see section 3
│  └─ README.md                        install and update steps for both tools
├─ docs/skills/                        one human-facing page per skill
├─ tests/                              tests for the plugin itself (section 9)
├─ LICENSE
├─ THIRD_PARTY_NOTICES.md
├─ README.md / README.zh-TW.md
└─ docs/superpowers/specs/
```

Both marketplace manifests point at the same `plugins/fw-c-harness` directory, so the skills are maintained once.

`fw-harness-init` writes `extraKnownMarketplaces` into the firmware repo (`.claude/settings.json` and `.github/copilot-settings.json`), so team members are prompted to install the plugin after cloning.

**Division of responsibility:** the plugin carries only what should update with the plugin version (skills and templates). Rules, state, gate scripts, and git hooks are **written into the firmware repo and committed**, so people without the plugin, people committing by hand, and CI all follow the same rules.

## 3. Skills (13)

Every skill uses the `SKILL.md` format and follows the authoring conventions in section 3.4.

### 3.1 Harness lifecycle

| Skill | Invocation | Purpose |
|---|---|---|
| `fw-harness-init` | user | Generates the whole harness in a firmware repo (section 4), including ARCHITECTURE.md files derived from the actual directory tree (section 6). Detects existing files first and never overwrites them. |
| `fw-harness-upgrade` | user | After a plugin update, compares against `harness/.harness-version`. **Managed files** (scripts, hooks) are updated directly. **Team-owned files** (the incident and rule sections of AGENTS.md and CLAUDE.md) show a diff and ask item by item. |
| `fw-architecture-sync` | model | Used when `arch_check` fails: drafts ARCHITECTURE.md for new folders and refreshes observed dependencies. Approved rules still need a human. |

### 3.2 Work loop

| Skill | Invocation | Purpose |
|---|---|---|
| `fw-session-start` | user | Six steps: confirm location and git identity → run `init` → read your own handoff → read recent progress and `git log` → list candidate tickets (your active ticket first) → **confirm the ticket with the user before writing code**. |
| `fw-ticket` | model | Create, claim, move, and add evidence. Every write goes through `harness/scripts/ticket.py`, which fills in identity and time and enforces the transition rules (section 5.4). |
| `fw-hil-verify` | user | Pays off the board-level debt of a `verifying` ticket: guides flashing and serial capture, stores the log under `harness/evidence/`, and records `kind: hil` evidence. A human flashes the board; the skill supplies commands and collects evidence. |
| `fw-done` | user | Five steps: read the diff → update `harness/handoff/<slug>.md` → add a round to `harness/progress/` → update the ticket → draft a commit message containing the ticket ID, in the configured language. **It displays the message and leaves committing to the user.** |

### 3.3 Implementation and review

Adapted from awesome-copilot (MIT); each file credits its source.

| Skill | Invocation | Source | Purpose |
|---|---|---|---|
| `fw-c-implement` | model | `agents/expert-embedded-c-engineer.agent.md` | Read the ticket and the relevant ARCHITECTURE.md → write a Unity test and watch it fail → implement → run `check` → record evidence. References: `embedded-c-rules.md` (fixed-width types, `const`, `static`, macros, error return codes), `isr-concurrency.md` (`volatile`, critical sections, what an ISR must avoid), `memory-budget.md` (dynamic allocation limits, stack, map budget), `module-template.md` (`.h`/`.c` skeleton). |
| `fw-c-review` | model | `instructions/code-review-generic.instructions.md` (severity and format), `skills/security-review/SKILL.md` (self-verification), mattpocock `code-review` (two axes) | Two-axis review, each axis in its own sub-agent, reported side by side (section 7). |
| `fw-c-test-gap` | model | `skills/test-gap-audit/SKILL.md` | Read-only test gap audit with P0 to P3 severity. Keeps the source's evidence standard: a cited line must contain what it is cited for, and every number comes with the command that produced it. |
| `fw-c-debug` | model | `skills/engineering/diagnosing-bugs` (mattpocock/skills), with `skills/bug-reproduction-brief` and `agents/gem-debugger.agent.md` | Build a loop that goes red before hypothesising, rank falsifiable hypotheses, prove one. Adds HardFault register decoding, stack overflow, ISR races, `git bisect`, and a human-in-the-loop script for board steps. Every fix lands with a regression test. |
| `fw-misra-deviation` | model | deviation section of `expert-embedded-c-engineer` | When a MISRA rule must be broken, writes `docs/deviations/DEV-NNNN.md` (rule number, rationale, risk, scope, approver). The approver is someone other than the author. |
| `fw-guide` | user | mattpocock `ask-matt` (router pattern) | Router: names every other skill and when to reach for it, so people remember one skill instead of thirteen. |

### 3.4 Skill authoring conventions

Based on mattpocock/skills `writing-for-agents`:

- **Invocation is a deliberate choice.** A user-invoked skill sets `disable-model-invocation: true` and costs no context load; its `description` is a one-line human summary. A model-invoked skill keeps a model-facing `description` that front-loads its trigger words, one trigger per distinct case. Choose model invocation only when the agent or another skill must reach the skill on its own.
- **Short `SKILL.md`, disclosed reference.** `SKILL.md` holds the steps and the reference every branch needs. Material only some branches need moves to a sibling file behind a pointer that says when to read it.
- **Every step ends on a completion criterion** the agent can check, worded to demand thorough work ("every changed function accounted for").
- **Positive phrasing.** State the target behaviour. A prohibition appears only as a hard guardrail, paired with the positive target.
- **Single source of truth.** Each rule lives in one place; skills point at harness files (for example `harness/review-policy.json`) instead of restating them.
- **No em-dashes** in any prose.
- Each promoted skill has a page under `docs/skills/<skill>.md` with **What it does**, **When to reach for it**, **Common questions**, and **It's working if**.

## 4. Harness written into the firmware repo

```
<fw-repo>/
├─ AGENTS.md                         shared entry point (read by Copilot, Claude, and others)
├─ CLAUDE.md                         authoritative handbook
├─ ARCHITECTURE.md                   top-level map (section 6)
├─ <each code folder>/ARCHITECTURE.md generated from the actual tree
├─ .github/
│  ├─ copilot-instructions.md        one line: read AGENTS.md first
│  └─ instructions/c-fw-review.instructions.md   applyTo: "**/*.{c,h}", for Copilot PR review on GitHub
├─ .claude/settings.json             extraKnownMarketplaces
├─ .githooks/                        commit-msg, post-commit, post-merge
├─ Makefile                          check target: thin wrapper
├─ init.sh / init.ps1                thin wrappers
├─ .clang-format
├─ docs/
│  ├─ references/*.llms.txt          MCU SDK / RTOS notes
│  └─ deviations/                    MISRA deviation records
└─ harness/
   ├─ .harness-version
   ├─ config.json                    toolchain paths, CMake presets, size budget, cppcheck args, language
   ├─ architecture.json              approved layers and dependency rules, plus grandfather list
   ├─ review-policy.json             section 7
   ├─ people.json                    optional: email → slug / display name
   ├─ cppcheck-suppressions.txt      ratchet: may only shrink
   ├─ tickets/FW-NNNN.json           one file per ticket
   ├─ progress/<YYYY-MM-DD>_<slug>_<n>.md
   ├─ handoff/<slug>.md
   ├─ reviews/FW-NNNN_<slug>_<YYYY-MM-DD>.md
   ├─ evidence/                      large evidence such as HIL logs
   └─ scripts/                       Python 3, the only implementation of gate and state logic
```

### 4.1 Entry points: AGENTS.md → CLAUDE.md

**AGENTS.md** (short):

- Which directories may be edited. Vendor and generated code is marked read-only by its ARCHITECTURE.md.
- Hard guardrails: `git clean`, `git push`, `--no-verify`; editing linker scripts, startup files, approved rules in `harness/architecture.json`, or adding to `cppcheck-suppressions.txt` (entries may only be removed); marking a ticket `done`.
- Windows notes: the Python launcher (`py -3` versus the Microsoft Store stub), legacy console code pages such as cp950 (scripts always read and write UTF-8), Git Bash versus PowerShell.
- A pointer to CLAUDE.md.

**CLAUDE.md**, four parts:

1. **Session start**: the six steps of `fw-session-start`.
2. **Working rules**: one active ticket per person; run `check` on the merged tree before merging; add new C files to CMake, not just to disk; leave compiler flags as they are.
3. **Definition of Done**: section 5.4.
4. **The why behind design decisions**: a rationale for every flag and gate. The template includes an incident format (date, what happened, which rule grew from it), left empty for the team to fill.

### 4.2 Verification gates

The **only implementation** is `harness/scripts/check.py`. `Makefile`, `init.sh`, and `init.ps1` are thin wrappers around it and **add no flags of their own**.

`init` (run at the start of every session; it verifies and never installs):

1. Python 3 is available
2. `git config user.name/email` is set (fails otherwise, because identity is the basis of collaboration)
3. `core.hooksPath` points at `.githooks`
4. Tools exist and their versions are logged: `arm-none-eabi-gcc`, `gcc`, `cmake`, `cppcheck`, `clang-format`
5. The `harness/` layout and JSON schemas are valid
6. `check` runs once

The log goes to `.verify_logs/<timestamp>.log` (gitignored).

`check` runs these in order and stops at the first failure:

1. `clang-format --dry-run --Werror` on changed C sources: files that differ from the merge base with `origin/main` (or from HEAD when `origin/main` is absent), plus untracked ones, skipping vendor and generated modules
2. `cppcheck` with `harness/cppcheck-suppressions.txt`
3. `arch_check` (section 6.3)
4. `ticket_check` (section 5.5)
5. Cross build (`target` preset, `-Wall -Wextra -Werror`)
6. Host Unity tests (`host-test` preset)
7. Size budget: run the size tool (for example `arm-none-eabi-size`) on the ELF and read its Berkeley output; flash is `text + data`, RAM is `data + bss`, and either exceeding its budget in `config.json` fails

Every command lives in `harness/config.json` as an argv array (the token `{python}` expands to the running interpreter), so a team swaps tools without touching the scripts. A missing tool fails its step with an install hint.

`check.py --record FW-NNNN` writes the result as `kind: check` evidence on that ticket, with HEAD as the commit and `passed` set from the outcome. It refuses to run on a dirty working tree, so the evidence always describes a real commit.

**Ratchet:** `cppcheck-suppressions.txt` and the grandfather list in `architecture.json` may only shrink. Step 2 checks the former and step 3 the latter against `origin/main`, failing on any new entry. Without `origin/main`, both compare against HEAD and warn. A list that does not exist at the baseline yet is being introduced, so nothing in it counts as new.

### 4.3 git hooks (instead of a Claude-only PostToolUse hook)

git hooks behave the same whether a person, Copilot, or Claude makes the commit.

| Hook | Purpose |
|---|---|
| `commit-msg` | The message contains `FW-NNNN` or starts with `harness:` / `chore:`; every referenced ticket exists in `harness/tickets/`. |
| `post-commit` | Regenerates the `feature_list.json` index. **Touches no tracked file**, so the working tree stays clean after a commit. |
| `post-merge` | Regenerates the index and runs `ticket_check`, suggesting `ticket.py renumber` when IDs clash. |

**Commit evidence is never written into ticket files.** The index derives it from `git log` each time it is built. Writing evidence from a hook dirties the working tree and causes merge conflicts once several people commit, so it is computed instead. Ticket files store only evidence git cannot derive (`check`, `hil`, `review`).

## 5. State and identity

### 5.1 Identity

- Source: `git config user.name` and `user.email`. There is no separate account system.
- Slug (used in file names): the email local part; if it contains `+`, the part after `+`; lowercased, with every character outside `[a-z0-9-]` replaced by `-`. `harness/people.json` can override it.
- Every script that writes state fills in the identity itself. No command accepts an identity argument.

### 5.2 Ticket file `harness/tickets/FW-NNNN.json`

```json
{
  "id": "FW-0042",
  "title": "UART driver supports DMA receive",
  "area": "drivers/uart",
  "status": "active",
  "priority": 2,
  "requires_hil": true,
  "created_by": {"name": "Alice Chen", "email": "alice@example.com"},
  "created_at": "2026-09-15T10:02:00+08:00",
  "assignee": {"name": "Alice Chen", "email": "alice@example.com"},
  "user_visible_behavior": "Receives 4 KB continuously at 115200 baud without dropping a byte",
  "verification_steps": ["host test: ring buffer overflow returns an error code", "on board: 4 KB loopback, CRC matches"],
  "dod_pending": ["on-board loopback verification"],
  "evidence": [
    {"kind": "check", "by": {...}, "at": "...", "commit": "a1b2c3d4e5", "summary": "check 7/7 passed", "passed": true},
    {"kind": "review", "by": {...}, "at": "...", "ref": "harness/reviews/FW-0042_bob_2026-09-16.md", "open_critical": 0},
    {"kind": "hil", "by": {...}, "at": "...", "ref": "harness/evidence/FW-0042/loopback.log"}
  ],
  "history": [
    {"by": {...}, "at": "...", "from": "next", "to": "active", "note": ""}
  ],
  "blocked_reason": null,
  "notes": ""
}
```

The index `feature_list.json` is generated by a script and **gitignored**. It summarises every ticket and adds the derived commit evidence, so an agent can scan the queue quickly.

### 5.3 Ticket ID allocation

- A new ID is `max(local tickets, origin/main tickets) + 1`. The script runs `git fetch origin main` first; offline, it uses the local maximum and warns.
- An ID is **claimed only once the commit creating the ticket is merged into main**.
- When two branches both add `harness/tickets/FW-0096.json`, git reports an add/add conflict at merge time instead of silently overwriting.
- Before merging, `ticket.py collisions` fetches and compares `created_by` and `created_at` of same-numbered tickets locally and on `origin/main`; a difference is a clash. `ticket.py renumber FW-0096` moves the local ticket to the next free ID and lists branch commits whose messages still reference the old ID.

### 5.4 State machine and Definition of Done

```
backlog → next → active → verifying → done
   ↘       ↘       ↘          ↘
     blocked (from any state except done; requires blocked_reason; unblocking returns to the previous state)
```

| Transition | Condition (enforced by `ticket.py`) |
|---|---|
| → `active` | The actor becomes the assignee; that person has no other `active` ticket |
| `active` → `verifying` | At least one `kind: check` with `passed: true` whose commit is HEAD or an ancestor of HEAD |
| `verifying` → `done` | `dod_pending` is empty; `kind: hil` exists when `requires_hil` is true; the **latest** `kind: review` is by someone other than the assignee with `open_critical == 0`; the CLI runs in an interactive terminal (TTY) and the ticket ID is typed to confirm |

"Written" and "done" are distinct: when code is written and `check` passes but board verification or review is still owed, the ticket stays in `verifying` with the debt listed in `dod_pending`.

**Only a human marks a ticket `done`.** AGENTS.md states it, `fw-ticket` declines to do it, and `ticket.py move <id> done` requires a TTY on stdin (an agent's shell usually has none) plus typed confirmation. Mechanically, `ticket_check` can verify that a `done` ticket has HIL evidence and a review by someone else, but it cannot prove a human produced that evidence. CLAUDE.md states this limit; PR review is the final safeguard.

### 5.5 `ticket_check` (runs inside `check`)

- Every ticket file matches the schema; IDs are unique and match file names
- Each assignee has at most one `active` ticket
- Every `done` ticket satisfies section 5.4
- Every `blocked` ticket has a `blocked_reason`

### 5.6 Progress and handoff

- `harness/progress/<YYYY-MM-DD>_<slug>_<n>.md`: one file per session, with author, ticket ID, and start and end commits in the header, and the `check` summary as evidence. One file per person per session, so they never conflict.
- `harness/handoff/<slug>.md`: one per person, overwritten each time: goal, what was done, blockers, suggested next step.
- When someone takes over another person's ticket, `fw-session-start` also reads the previous assignee's handoff.

## 6. ARCHITECTURE.md generation and sync

### 6.1 Generation (`fw-harness-init`, `fw-architecture-sync`)

1. **Scan**: every folder containing `.c`/`.h` files is a candidate. Exclude `build/`, `out/`, `Debug/`, `Release/`, `.git/`, and anything in `.gitignore`. Default depth is two levels; go deeper only when a folder has more C files than the threshold in `config.json` (default 30) and its subfolders have distinct responsibilities.
2. **Classify**:
   - **Owned code**: full document
   - **Vendor or generated code**: detected by name (`third_party`, `vendor`, `CMSIS`, `Drivers/STM32*`, and so on) or a "generated" marker in file headers; short document stating read-only status, source and version, and how to upgrade
   - **Tests**: framework, naming conventions, how to run
3. **Dependency analysis**: parse `#include "..."`, map includes to folders through the CMake include paths, build the folder dependency graph, and list cycles and likely reverse dependencies.
4. **Draft contents**: responsibility (inferred from file names, function names, and existing comments, marked as inferred), entry points, **observed dependencies**, **approved dependencies (empty, awaiting a human)**, ISR and memory notes.
5. **Confirmation**: init ends by listing the inferred layer order and asks the user to confirm or adjust each item, then writes `harness/architecture.json`. Existing violations go into the grandfather list.

### 6.2 Source of truth

`harness/architecture.json` is the single source of approved rules. The approved-dependency table in each ARCHITECTURE.md is generated from it inside a marked block; scripts rewrite only the marked block and leave the human-written sections alone.

```json
{
  "version": 1,
  "include_dirs": ["src/app", "src/drivers", "src/hal", "third_party/cmsis/Include"],
  "modules": {
    "src/app": {"kind": "owned", "allowed_deps": ["src/drivers"]},
    "src/drivers": {"kind": "owned", "allowed_deps": ["src/hal"]},
    "src/hal": {"kind": "owned", "allowed_deps": ["third_party/cmsis"]},
    "third_party/cmsis": {"kind": "vendor", "allowed_deps": []},
    "test": {"kind": "test", "allowed_deps": []}
  },
  "grandfathered": ["src/hal -> src/app"]
}
```

- A module is a repo-relative folder; a file belongs to the module with the longest matching path.
- `kind` is `owned`, `vendor`, `generated`, or `test`. Only `owned` modules have their includes checked; `vendor` and `generated` modules are read-only and skipped by the format step.
- Includes (`"..."` and `<...>`) resolve against the including file's folder, then `include_dirs` in order. Unresolved includes are system or toolchain headers and are ignored.

### 6.3 `arch_check`

| Situation | Result |
|---|---|
| A folder with C files has no ARCHITECTURE.md and is not listed in `architecture.json` | fail |
| An `#include` breaks an approved rule and is not grandfathered | fail |
| The grandfather list has entries not on `origin/main` | fail |
| An ARCHITECTURE.md marked block disagrees with the json | fail (suggests regenerating) |
| A deleted folder is still listed in the json or docs | warning |

## 7. Review policy

`harness/review-policy.json`:

```json
{
  "misra": {"standard": "MISRA C:2012", "mode": "advisory"},
  "block_on": ["critical"],
  "forbid_self_review": true
}
```

The report language comes from `language` in `harness/config.json`.

`misra.mode` is `off`, `advisory` (default), or `required`:

- `advisory`: MISRA findings rank at most 🟢 and never block a merge
- `required`: breaking a required rule without a deviation record ranks 🔴

`fw-c-review` reviews the diff since a fixed point along **two axes**, each in its own sub-agent so neither pollutes the other, and reports them side by side without merging or reranking:

- **Standards**: does the code follow the C/firmware checklist, the approved layering, and the MISRA mode?
- **Spec**: does the code deliver the ticket's `user_visible_behavior` and `verification_steps`? It reports missing or partial requirements, behaviour nobody asked for, and requirements that look implemented incorrectly.

Standards severity:

- 🔴 **Critical (blocks merge)**: undefined behaviour, array or pointer out of bounds, integer overflow causing wrong results, data shared between an ISR and the main loop without protection, a missing `volatile`, an ignored error return code, an unvalidated external length, an open debug port or hard-coded key, a layering violation that is not grandfathered
- 🟡 **Important**: new logic without tests, resources not released, blocking calls on time-critical paths, magic numbers standing in for register addresses
- 🟢 **Suggestion**: naming, comments, readability, MISRA advisory

Report format (`harness/reviews/FW-NNNN_<reviewer-slug>_<date>.md`): the header records the reviewer identity, ticket ID, and reviewed commit range; a severity count table comes first; each finding has severity, `path:line`, the problem, why it matters, a suggested fix, and confidence. Every finding is self-verified (re-read the code and rule out a false positive handled upstream). Patches are proposed for a human to apply.

After a review, `fw-ticket` records `kind: review` evidence with `open_critical` taken from the report. After fixes, a new review produces a new report and new evidence; the latest one counts.

`.github/instructions/c-fw-review.instructions.md` is a condensed version of the same checklist for Copilot PR review on GitHub. `fw-harness-init` generates it from the same source so the two stay consistent.

## 8. Error handling

- Every script exits non-zero on failure and says which check failed, which file, and how to fix it.
- All reads and writes use UTF-8, regardless of the Windows console code page.
- Ticket writes go read → modify → write temporary file → rename, so a crash never leaves a half-written file.
- Offline (`git fetch` fails): ID allocation and ratchet comparison fall back to local data and warn explicitly.
- When `fw-harness-init` finds an existing file with the same name, it leaves the file alone, writes `<name>.harness-proposed`, and lists the differences.

## 9. Testing the plugin

- The Python in `harness/scripts/` is tested with pytest: identity slugs, ID allocation and renumbering, transition rules, include dependency parsing, ratchet comparison, index generation.
- Tests isolate the contributor's global git configuration, so a personal `~/.gitconfig` cannot change the results.
- `tests/fixtures/sample-fw/`: a small CMake C project with a vendor folder, one deliberate reverse dependency, and Unity tests. The end-to-end test copies it to a temporary directory, runs init generation, and checks both passing and failing `check` scenarios.
- Two git identities simulate parallel work: clashing ticket IDs, separate active tickets, and cross review, exercising section 5.
- Skills cannot be tested automatically, so a manual checklist runs the full loop once in Claude Code and once in Copilot (init → session-start → ticket → implement → review → done).

## 10. Rollout

1. Finish the plugin against `sample-fw` and pass section 9.
2. Pilot it on a real firmware repo with one or two people for two weeks, collecting the first incident-driven rules for CLAUDE.md.
3. Adjust from pilot feedback, publish the repo on GitHub, and document installation.
